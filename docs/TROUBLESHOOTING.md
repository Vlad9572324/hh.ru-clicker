# Troubleshooting — hh.ru-clicker (web-flow + mobile API)

Руководство по диагностике и починке типовых проблем дашборда. Два канала к HH:

- **web-flow** — браузерные cookies hh.ru (`data/browser_sessions.json`), парсинг SSR/HTML;
- **mobile/OAuth** — Bearer-токен `api.hh.ru` (`data/oauth_tokens.json`), добывается через cookies-authorize или OTP-логин (ветка `pr20`).

Каждая секция: **Симптомы → Причина → Решение/обход**. В конце — таблица «симптом → секция».

> Источники: git-история (`git log --all`), `AUDIT_REPORT.md`, код `app/*`. Файла `bugs_fixed_log.md` в репозитории не существует — история багов реконструирована по коммитам; где конкретику подтвердить не удалось, помечено «не подтверждено».

## 0. Куда смотреть сначала: диагностика

| Инструмент | Что даёт |

## 1. OAuth-токен протух / не получается

### 1.1 Токен истёк, отклики через API не идут

**Симптомы**

- В логе `OAuth: invalidated token for <hash> (auth_error)`, затем повторяющиеся неудачные obtain'ы.
- `GET /api/account/{idx}/oauth_status` → `{"has_token": false}` или отрицательный `expires_in_hours`.
- Отклики через OAuth возвращают `auth_error`; UI-бейдж аккаунта переключается на «cookies истекли» / «Degraded OAuth-режим».

**Причина**

- `access_token` живёт ~14 дней (`expires_in` до 1209599 с, `app/oauth.py`).
- Refresh у HH **single-use**: два параллельных refresh одним `refresh_token` инвалидируют один из них (поэтому в коде per-resume_hash refresh-локи).
- Если аккаунт долго стоит на паузе (лимит HH / ручная пауза), `refresh_token` сам успевает истечь (~2 недели) — тогда без cookies уже не авторизоваться (`37df156`).

**Что уже делает бот**

- Lazy-refresh при каждом OAuth-вызове (`_obtain_oauth_token`): кэш → refresh → полный authorize-flow через cookies аккаунта (GET `hh.ru/oauth/authorize`, при необходимости POST approve-формы).
- Proactive refresh worker: каждые 6 ч обновляет токены, у которых до истечения < 48 ч; первый запуск через 60 с после старта (`37df156`).
- На 401/403 от `api.hh.ru` кэшированный токен сбрасывается (`invalidate_oauth_token`), чтобы следующий вызов пошёл refresh'иться, а не долбил тем же мёртвым токеном (`app/oauth.py::_oauth_apply`).

**Решение (действия пользователя)**

1. Дашборд → раздел **«🔍 Аудит резюме»** → выбрать аккаунт в дропдауне → блок **«🔑 OAuth API»** → кнопка **«Получить токен»** (`POST /api/account/{idx}/oauth_token`). Статус покажет `✅ Токен получен | Nч осталось | refresh: да/нет`.
2. Если не получилось — **cookies аккаунта должны быть живыми** (полный authorize-flow ходит под ними). Обновите cookies из браузера и повторите.
3. В ветке `pr20` доступен OTP-вход без cookies: секция **«📱 Авторизация по телефону / email»** (см. секцию 11).
4. Крайний случай: удалить запись токена для resume_hash из `data/oauth_tokens.json` и получить заново.

### 1.2 `has_refresh: false`

Токен есть, но без `refresh_token` — он не продлится и умрёт по TTL. Получите токен заново (кнопка «Получить токен» / OTP), чтобы был полный комплект `access_token + refresh_token`.

### 1.3 Бот завис целиком после инвалидации токена (issue #19, ИСПРАВЛЕНО)

**Симптомы (исторические, до фикса `a2f6890`)**: после `OAuth: invalidated token …` дашборд намертво зависал — HTTP API, WebSocket и UI не отвечали, помогал только рестарт.

**Причина**: deadlock — `invalidate_oauth_token` удерживал `_oauth_lock` и внутри вызывал `_save_oauth_tokens()`, который пытался взять тот же `threading.Lock` (не re-entrant). Висел поток инвалидации, затем все потребители `_oauth_lock` (`get_oauth_status` и др.).

**Статус**: исправлено в `a2f6890` (save вынесен за пределы лока), регресс-тест `tests/test_oauth_invalidate_deadlock.py` (инвалидация обязана завершиться за 3 с). Если симптом воспроизводится на свежем коде — это новый deadlock, нужен дамп потоков (`faulthandler`).

## 2. Mobile API 401 (Bearer api.hh.ru)

**Симптомы**

- В `data/diag.log` записи с тегом `auth`/`blocked`, статус 401/403 на запросы к `api.hh.ru`.
- В `debug.log`: `OAuth apply auth_error for <hash> vid=…`, `OAuth: invalidated token …`.
- `sent` не растёт при откликах через API.

**Причина**: Bearer-токен отклонён HH — истёк и refresh не прошёл, либо отозван (смена пароля, logout на устройстве, подозрение на аккаунт).

**Реальное поведение кода (HEAD `b3bba5a`, читать `app/oauth.py`, `app/hh_client_factory.py`, `app/manager.py`)**

1. `_oauth_apply` на 401/403 вызывает `invalidate_oauth_token(...)` и возвращает `auth_error` — иначе менеджер переиспользовал бы rejected-токен в бесконечной петле 401.
2. Следующий OAuth-вызов автоматически проходит цепочку refresh → cookie-authorize (секция 1.1).
3. **Fallback на web существует на двух уровнях:**
   - **Выбор клиента** (`app/hh_client_factory.py::get_client`): при `mode="auto"` (дефолт `CONFIG.default_client_mode="auto"`) аккаунт получает `MobileHHClient`, только если есть живой OAuth-токен (`oauth.get_oauth_status(...)["has_token"]`), иначе — `WebHHClient`. Нет токена → автоматически web. Режим форсируется полем `account["mode"]` (`"web" | "mobile" | "auto"`), неизвестный mode трактуется как `"web"`.
   - **Apply-пайплайн**: если cookies живые и нет флага `use_oauth`/`use_oauth_apply`, отклики идут web-путём. И наоборот, при мёртвых cookies и живом токене включается **degraded OAuth-режим** (`7843ce7`, `a71158e`, `cd002d7`): чекбокс на карточке аккаунта **«🔑 OAuth-fallback при протухших cookies»** (`degraded_fallback_enabled`, default ON, `POST /api/account/{idx}/degraded_fallback`). В degraded-режиме вакансии собираются через `GET /vacancies`, отклики через `POST /negotiations`; пропускаются вакансии с `has_test`/`response_letter_required` (без cookies их не пройти) — счётчик пропусков виден в бейдже. Первый `auth_error` в цикле прерывает apply-фазу, чтобы не флудить HH мёртвыми cookies (`cd002d7`).
4. **Важно для фазы рефакторинга**: на HEAD `MobileHHClient` — skeleton (Phase 0): реально работают `fetch_counters()` и OAuth-extras (делегация в `app/oauth.py`), остальные методы бросают `NotImplementedError("phase N: …")`. Обработка 401 в переговорах/откликах mobile-клиента появится в фазах 2–4; сегодня 401 на этих путях — это «метод ещё не реализован», а не баг авторизации.

**Действия пользователя**

1. Проверить статус: `GET /api/account/{idx}/oauth_status` или чип OAuth на карточке.
2. Перевыпустить токен (секция 1.1: «Получить токен», либо свежие cookies, либо OTP в `pr20`).
3. Если OAuth недоступен сознательно — перевести аккаунт в web (`mode="web"` / снять флаг «🔑API» на карточке, кнопка-тумблер `🔑API/🌐Web`).
4. Если 401 сопровождается `ddos_guard`/`blocked` в diag.log — это уже не токен, а секция 3.

## 3. DDoS-Guard soft-ban (403/404/JS-challenge)

**Симптомы**

- 403/404 от hh.ru при **заведомо живых cookies** (те же cookies в браузере работают).
- `diag.log` с тегами `ddos_guard` / `blocked` / `captcha`; в ответах маркеры `ddos-guard`, `ddg1`, JS-challenge; заголовок `server: ddos-guard`.
- Ошибка добавления сессии (исторически issue #8): валидатор сразу получал 403.
- Капча: `batch_update: сервер отдал hhcaptcha/recaptcha isBot=true` в debug.log.

**Причина**

DDoS-Guard перед HH фингерпринтит клиента по JA3/JA4 TLS + HTTP/2 SETTINGS + порядку заголовков **до чтения cookies**. Голый python `requests`/urllib3 не похож на браузер → 403/404. Отдельно существует soft-ban по IP: тот же клиент с того же IP, что «спалился», режется некоторое время даже с правильным фингерпринтом. Эндпоинт `/applicant/resumes` проверяет cookies отдельно от TLS-гейта, поэтому 403 возможен даже при пройденном фингерпринте, если cookies протухли (`5c1e3a9`).

**Что уже сделано в проекте**

- **TLS/H2-имперсонация Chrome через curl_cffi** (`1b750d7`): все горячие HTTP-пути (oauth, apply, chat, negotiations, resume, manager) ходят через обёртку `app/hh_http.py` (Chrome 124 по умолчанию, переопределение env `HH_IMPERSONATE=chrome131` и т.п.). Если curl_cffi не установлен — silent fallback на `requests` (имперсонация отсутствует!). Проверка: `GET /api/proxy/info` → поле `impersonate`.
- **Валидация добавляемых сессий через тот же клиент** (`1d01b67`) + **warm-up GET к `hh.ru/`** для получения DDoS-Guard-кук перед профайлингом (`dbc7a8a`, фикс issue #8). Ошибка валидации теперь подсказывает: 404 ≈ soft-ban IP+фингерпринт, а не «плохие cookies»; без curl_cffi — совет установить его.
- Если HH всё равно вернул 401/403 при добавлении сессии, backend возвращает `can_force=true`, и UI рисует кнопку **«Добавить всё равно»** (`dbc7a8a`, issue #8) — править `data/browser_sessions.json` руками больше не нужно.
- **Прокси** (`f1ffe22`, `c82de6c`, `b3bba5a`): см. ниже.

**Решение (действия пользователя)**

1. **Проверить impersonate**: Настройки → Подключение → секция **«🌐 Прокси и исходящий IP»** → кнопка **«↻ Проверить»**. Если `impersonate` пустой — поставить `curl_cffi` (`pip install -r requirements.txt`, рестарт бота; в Docker уже в образе).
2. **Сменить исходящий IP прокси**: поле ввода прокси в той же секции → `socks5h://host:port` или `http://host:port` → **«💾 Применить»**. Перед сохранением бот делает probe (api.ipify.org): нерабочий прокси откатывается, рабочая конфигурация не портится (`b3bba5a`, `POST /api/proxy/set`). Альтернатива: env `HH_PROXY=socks5h://…` + рестарт.
3. В `docker-compose.yml` есть готовый **sing-box sidecar** (VLESS/Reality outbound, SOCKS5 inbound на `socks5h://singbox:1080`) — включить, если свой прокси не настроен (`f1ffe22`).
4. Дать IP «остыть» (soft-ban временный) и/или добавить сессию через «Добавить всё равно».
5. Если в diag.log тег `captcha` — аккаунт упёрся в hhcaptcha; автоматического решения нет, нужно снизить активность (см. секцию 6 про auto-pause) и пройти капчу в браузере вручную.

## 4. Chatik: слетевшие cookies / 401 в чатах

### 4.1 Cookies чатиков «wipe» после mobile-блока (issue #20, блокер 2, ИСПРАВЛЕНО)

**Симптомы (исторические, на ветке pr20 до фикса `41656cc`)**: после включения mobile OTP-фич чатики начали отваливаться — списки чатов/история/quick_replies возвращали ошибки, отправка сообщений деградировала, cookies чатиков приходилось пере-получать.

**Причина**: все запросы к `chatik.hh.ru` ходили с `mobile_user_agent()` / «WebView» UA, который содержал идентичность Android-приложения (`ru.hh.android/… Device: …`). Chatik — **web-продукт** и ожидает браузерную идентичность; UA мобильного приложения вызывал отторжение/перевыпуск серверных сессий.

**Фикс (`41656cc`)**: `webview_user_agent()` теперь возвращает **только** desktop-идентичность (без Android-хвоста); на него переведены все chatik-пути: warm-up за cookies, `_fetch_chat_list`, `_fetch_chat_history`, `fetch_quick_replies`, `send_participant_action` (TYPING), `mark_chat_read`, `send_negotiation_message`, `fetch_chatik_ws_url` и WS-клиент.

**Действия пользователя**: после обновления ничего делать не нужно. Если чаты всё ещё 401-ят на актуальном коде — обновить cookies сессии и дать `_ensure_chatik_cookies` пере-получить `hhuid`/`crypted_hhuid`.

### 4.2 Сопутствующее: гонка воркеров за cookies (swarm-1 #8)

Несколько воркеров одного аккаунта (apply + stats + LLM) могли одновременно перепрошивать cookies → взаимное затирание → 401. `_ensure_chatik_cookies` сериализован через `acc["_cookies_lock"]` с double-checked locking (`app/hh_chat.py`). Лечить не нужно, но при повторных «беспричинных» 401 чатиков смотреть в debug.log строки `_ensure_chatik_cookies`.

## 5. Отклик ушёл, но `sent` не вырос (200 + SPA HTML вместо JSON)

**Симптомы**

- Отклик фактически отправлен (виден на hh.ru), но счётчик `sent` не растёт, в логе ошибка классификации.
- В debug.log «непонятный 200»: первые 200 байт тела с `DOCTYPE`/`<html`.

**Причина**: HH после `POST /popup` иногда редиректит на страницу `/vacancy/{id}` с SPA-обёрткой (18–20 KB HTML) — топик отклика там не отдаётся. Раньше классификатор считал это ошибкой (`b1385d7`).

**Решение**: исправлено в `b1385d7` — `classify_apply_response` трактует 200 + HTML >2 KB **без** error-маркеров (`error`, `test-required`, `already-applied`, `limit`, `spam`, `captcha`) как `sent`; на непонятные 200 пишется начало тела в debug-лог для диагностики будущих смен формата HH. Действий пользователя не требует; если симптом вернулся — приложить хвост `debug.log` (виден реальный ответ HH).

## 6. Авто-пауза аккаунта / `sent=0` при успешных откликах

**Симптомы**

- Аккаунт в паузе с причиной `auto_errors`, лог: `⛔ Авто-пауза: N ошибок подряд. Снимите вручную.`
- Видимо-успешные отклики не засчитываются: пауза в середине батча отбрасывает все последующие успешные 200 (`if state.paused: break`).

**Причина (историческая, фикс `eb20a12`)**: HH транзитно возвращал `{"error":"unknown"}` на `POST /popup` (сбой на стороне сервера). Классификатор считал это ошибкой → 3 подряд `unknown` → auto-pause (порог был 3).

**Решение/настройка**

- Исправлено: `unknown` больше **не** растит `consecutive_errors` (только счётчик ошибок для UI); коммит-сообщение `eb20a12` также заявляет подъём порога с 3, однако текущий дефолт в коде — см. ниже (расхождение между сообщением коммита и `app/config.py`, точное промежуточное значение не подтверждено).
- Конфиг: `auto_pause_errors` (текущий дефолт **5** в `app/config.py`, 0 = выключить авто-паузу) — настраивается в UI.
- Снятие паузы: кнопка паузы на карточке аккаунта (вручную). Авто-пауза с причиной `auto_errors` и `limit` также снимается сама при rollover в полночь МСК (`_maybe_roll_daily_counter`), ручная пауза — никогда автоматически.

## 7. Лимит откликов HH (`negotiations-limit-exceeded`)

**Симптомы**

- `🛑 HH daily-limit 200 достигнут (N откликов). Пауза.`, бейдж `HH-лимит: N/200. Сброс в 00:00 МСК`.
- Исторически: пауза «залипала» на дни после полуночи (`9deadbe` — не выставлялся `paused_reason='limit'`, и rollover её не снимал; `37c608f` — `daily_date` в Docker штамповался UTC вместо МСК, rollover не срабатывал после рестарта). Оба бага исправлены.

**Механика сейчас**

- Конфиг: `hh_daily_limit` (default **200**), `stop_on_hh_limit` (default **true** — полная остановка аккаунта при лимите, без перепроверок).
- **Лимит-трекер** (`ca7acbc`, worker каждые 30 мин): реальное число сегодняшних откликов тянется через OAuth (`GET /negotiations`-счётчики), а не угадывается. Auto-recovery: если аккаунт стоит в limit-stop, а фактический счёт < лимита−5 — пауза/hard-stop снимаются сами, не дожидаясь полуночи.
- Лимит HH действует **только на новые отклики**: LLM-ответы в уже открытых переговорах продолжают работать и в паузе (`6c4ff4a`, reason-aware проверка паузы).
- Сброс — в 00:00 МСК (зона `Europe/Moscow`).

**Действия пользователя**: обычно ждать полуночи МСК. Если пауза выглядит ложной — проверить чип реального счётчика на карточке; поднять `hh_daily_limit` в настройках **нельзя безопасно** (реальный лимит на стороне HH, а не в конфиге — конфиг лишь порог остановки).

## 8. Опросники и тесты при отклике

**Симптомы**

- Отклик классифицируется как `test`, в логе пропуск вакансии; popup `test-required` (`withoutTest=no`).
- Ложное «тест» вместо «нет авторизации» — исправлено аудитом (H2, `2097b6b`): страница логина определяется **до** парсинга, и возвращается `auth_error`.

**Поведение и настройка**

- По умолчанию вакансии с тестами/опросниками **пропускаются** (в т.ч. после 2 неудач заполнения — `_test_failures`).
- Включить прохождение: глобально `auto_apply_tests` в настройках, либо чекбокс **«apply tests»** на карточке аккаунта (`state.apply_tests`).
- Заполнение опросников LLM-ом: `llm_fill_questionnaire` (default false); дефолтный ответ без LLM — `questionnaire_default_answer` («Готова рассказать подробнее на собеседовании.»).
- Прогноз ответов без отправки: `GET /api/account/{idx}/test_llm_questionnaire?vacancy_id=…`.
- В **degraded OAuth-режиме** опросники/тесты не проходятся в принципе (нет cookie-контекста) — вакансии с `has_test` пропускаются со счётчиком `degraded_skipped` (`7843ce7`).

## 11. Мобильный OTP-логин (ветка `pr20`)

Мастер в UI: секция **«📱 Авторизация по телефону / email»** (Email/Телефон → «Отправить код» → код из SMS/письма → «Подтвердить»). При успехе: импортируются OAuth-токены (`oauth_tokens_imported`), собирается список резюме/вакансий, создаётся/обновляется браузерная сессия из mobile-токена (`create_browser_cookies`). Кнопки: «Отправить повторно», «Выйти / сбросить»; вложенный блок — настройки мобильного клиента (приоритет `web → environment → file → default`, источник виден у каждого поля; «💾 Сохранить», «✓ Проверить», «↻ Новый UUID», «Восстановить по умолчанию»).

Типовые проблемы и их фиксы в pr20 (issue #20):

| Блокер | Симптом | Причина → фикс |
|---|---|---|
| **1 — `decaeaf` fix(mobile_auth)** | При запросе/вводе OTP-кода дашборд подвисал на время сетевых вызовов. | Блокирующие HTTP-вызовы выполнялись прямо в async-хендлерах → вынесены в `run_in_threadpool`. |
| **2 — `41656cc` fix(chatik)** | Чатики отваливались после подключения mobile-блока. | Android-идентичность в UA web-чатиков → desktop UA (подробно — секция 4.1). |
| **3 — `890a98d` fix(user_agent)** | Изменил настройки мобильного клиента (в т.ч. User-Agent) и нажал «Сохранить» — изменения не применялись до рестарта. | `effective_config()`/`mobile_user_agent()` кэшировались `lru_cache` без инвалидации → добавлен `_invalidate_config_caches()` на save/reset. |
| **4 — `1155390` fix(oauth)** | OTP-логин проходил («успех»), но токены исчезали после рестарта. | Ошибка записи `oauth_tokens.json` (права/read-only ФС) молча глоталась → `_save_oauth_tokens()` возвращает bool, и импорт падает с явной ошибкой «Не удалось сохранить OAuth-токены на диске» (роут отдаёт её как HTTP 502) вместо тихой потери сессии. |

**Действия пользователя при неудачном OTP-логине**

1. Читать текст ошибки в `ma-status` (UI) — теперь они конкретные (см. таблицу выше и `_error` в `app/routes/mobile_auth.py`: ошибки HH проксируются 4xx, сетевые — 502).
2. «Токены получены, но не удалось безопасно обновить oauth_tokens.json» → проверить права на каталог `data/` (файл пишется 0600, нужен доступ на запись; в Docker volume должен быть смонтирован и owned пользователем контейнера).
3. Код не приходит → «Отправить повторно» (UI показывает таймер `can_request_code_again_in`); сменить тип phone/email.
4. После «Выйти / сбросить» токены других аккаунтов в `oauth_tokens.json` сохраняются (удаляется только запись данного логина).
